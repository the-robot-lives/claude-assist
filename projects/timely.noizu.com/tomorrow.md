### THE PULL-CLOBBER BUG — the most user-visible defect found this session
TimelyKit's pull path was overwriting unpushed local edits. Root cause, verified directly in `TimelyLocalStore.swift`: `shouldReplace(existing:with:)` compares `server_revision` *before* it ever looks at a timestamp - `if incoming.serverRevision != existing.serverRevision { return incoming.serverRevision > existing.serverRevision }`. `server_revision` is one counter per workspace incremented by every mutation from every device and every entity, so a client with anything queued sees an incoming row's revision jump ahead of its own watermark the moment **anyone** in the workspace does anything at all - not only when two devices race to edit the same row. This reframes it from "an edge case" to "the ordinary path": any user with one queued correction, while a colleague (or their own other device) syncs anything, would have their on-screen edit silently reverted, assumed it lost, redone it, and produced a duplicate.
- **Fixed** with a dedicated, explicit `preserveUnpushedEdits` parameter (default `false`, set `true` only on the pull path in `SyncEngine.apply(_:ChangeSet)`) that gates a check for a genuinely pending mutation before applying an incoming row over local content.
- Android had the same defect; also fixed. iOS verified the fix independently with a negative control (seed a stale precondition, confirm the bug reproduces, then confirm the fix prevents it) rather than only asserting the happy path.
- The fix is documented in `docs/SYNC-PROTOCOL.md` §7.1, which now also states the second thing worth knowing: **pull preservation and push-result adoption are opposite rules for a similarly-shaped situation.** A `conflict`/`rejected` push result must **adopt** the server's row rather than preserve the local one, because there the server has already adjudicated the very mutation still sitting in the queue - preserving would show a rejected edit on screen as though it had succeeded. "The row has a pending mutation" is **not** enough on its own to pick the right behavior, since both conditions can be true of the same row at once; an implementation needs a signal for *which code path it is on*, which is exactly what `preserveUnpushedEdits` is (TimelyKit's push-result handler never sets it, regardless of pending-mutation state). TimelyKit's first draft had this inverted and only an existing test caught it.

### NATIVE SSO (task #22) — done, verified directly against the backend source
SSO could not complete from a native app as deployed: the callback redirected to a relative web path, and neither `ASWebAuthenticationSession` (iOS) nor AppAuth (Android) return control to a native app on a same-host relative redirect - only on the app's own registered URL scheme. Fixed:
- **`SSO_REDIRECT_ALLOWLIST`**, an exact-match (not prefix) allow-list (`lib/timely/auth/sso_redirects.ex`). Deliberately not prefix matching - the module's own comment gives the exact bypass: `startsWith("com.noizu.timely://")` is satisfied by `com.noizu.timely://auth/callback@evil.example`. A target carrying its own query/fragment is refused outright, since the server appends `?code=…` itself.
- **PKCE on the app's OWN code exchange, not against the identity provider** - the backend is the OAuth client and holds the IdP secret; the app never talks to the IdP directly. PKCE exists because a custom URL scheme is claimed by pattern, not owned, so any app on the device could register the same scheme and intercept the redirect; the verifier is the one thing an interceptor never sees.
- **7 error codes on the same redirect scheme** (confirmed via `apps/ios/Sources/TimelyiOS/Auth/PKCE.swift`'s `SSOErrorCode` enum, which mirrors the backend's): `redirect_not_allowed`, `invalid_code_challenge`, `state_mismatch`, `not_provisioned`, `sso_unavailable`, `sso_failed`, `oidc_failed`. Errors arrive as `?error=<code>` on the same redirect success uses, deliberately - an error rendered as a web page would leave `ASWebAuthenticationSession` hanging with nothing to return to, the identical failure the native redirect was added to fix, reached a different way.
- Android converged on the recommended `https://` App Link over a custom URL scheme, since App Links are domain-verified and not claimable by another app - **verified directly, and now current**: `build.gradle.kts`, the manifest's intent filter, and the allow-list all agree, guarded by a dedicated test; see the SSO ops section below for the exact detail (a mismatch existed at an earlier point in this file's history and has since been closed). iOS deliberately stayed on a custom scheme instead - a recorded product decision, not an oversight (see "Operator actions required" below for why: no Team ID yet, and the Universal-Link API needs iOS 17.4 while the app targets 17.0).

## Key design decisions and why (the reasoning that evaporates if not written down)

- **Taxonomy ids are deterministic UUIDv5** over `(workspace_id, canonical_name)` — `client_id = uuidv5(workspace_id, "client:" + canon(name))`, similarly for project/ticket. Two offline devices independently creating "Acme" compute the *same* id and converge with no coordination on reconnect. This is the single most important trick in the sync protocol (SYNC-PROTOCOL §3.2). Event-like entities (time spans, screenshots, devices, vision analyses) use **UUIDv7** instead, because their leading timestamp keeps primary-key inserts append-mostly at scale — there's no "two devices mean the same thing" question for an event.
- **The sync cursor is a per-workspace `server_revision` watermark, not a timestamp.** Client clock skew, commit-visibility races, and same-millisecond ties all make timestamp-based cursors silently lose data under load; `server_revision` is assigned inside the same transaction that publishes the row, so revision order equals commit order (§5).
- **Entity-level last-write-wins, and its known, accepted cost**: a same-window edit to a *different* field than another device's edit is discarded, not merged — the whole row resolves to whichever `updated_at_effective` is later. Field-level merge is the documented v2 fix (§13, limitation 1), deferred deliberately because three independently hand-written clients have to agree on entity-level LWW correctly first. This is a real tradeoff, not an oversight — user story US-108 was written this session specifically to describe it honestly rather than let a future edit soften it into sounding fixed.
- **`entity_kind` lives on the `MutationResult` envelope, not on the row itself** (verified directly: `apps/backend/lib/timely/sync/mutations.ex:184-186`, `tag_entity_kind/2`, "Always present in the shape, even before `tag_entity_kind/2` fills it"). This is why it survives a rejection where `entity: null`. `Timely.Schema.Settings.Setting` already uses a `kind` field on the row itself for a different purpose — don't conflate the two.
- **Clients must OMIT `end` from a payload rather than serializing it as `null`, when they mean "don't touch this field."** Verified: `apps/backend/lib/timely/sync/mutations.ex:409` checks `Map.has_key?(payload, "end") and payload["end"] == nil` — presence-with-null means "reopen this span," absence means "leave it alone." A client that always serializes every field (the naive default for most JSON encoders) turns every ordinary update into an accidental reopen. This is exactly the kind of bug that a schema validator won't catch.
- **Screenshot image bytes default to never leaving the device**; metadata always syncs. Raw vision-LLM responses are treated as image-equivalent (a full-text transcription of the same pixels defeats the privacy promise) and are gated behind the *same* double gate as the bytes themselves (§10). This is already covered by an existing user story (US-071) — new work in this area should cross-reference it, not duplicate it.
- **macOS is the only capture agent.** iOS and Android are review/correction companions — they mint taxonomy rows and push mutations exactly like the desktop agent, but they never run background screenshot capture (§1 role table).
- **`canon()` conformance is a hard gate (§14), not a guideline.** All three implementations (Elixir, Swift, Kotlin) must pass every fixture case before being allowed to sync against a shared workspace, because a `canon()` divergence doesn't throw, doesn't log, and doesn't fail a sync — it silently mints two ids for one client, and nobody notices until an invoice is short weeks later.
- **The server distinguishes `null` from absent on some fields — a client may only send a value it actually knows.** `null` is a claim; absence is an admission of ignorance. Verified directly against `apps/backend/lib/timely/sync/mutations.ex`: `guard_reopen` tests `Map.has_key?(payload, "end") and payload["end"] == nil` to detect a deliberate reopen; `guard_locked` does the identical check on `locked_at` to detect a deliberate clear of a billing-approval lock. Known presence-sensitive fields today: `end` and `locked_at`. A client that naively always-serializes every field (the default for most JSON encoders) turns an ordinary title edit into an accidental reopen or an accidental lock-clear the moment another device has closed the span or locked the day and this client hasn't pulled yet.
  - **This was a real, late-discovered bug, not a hypothetical**: TimelyKit was unconditionally serializing `"locked_at": null`. Fixed centrally in `apps/shared/TimelyKit/Sources/TimelyKit/Store/WirePresence.swift` (verified present and implemented, not just planned) — `end` is sent-when-deliberately-cleared (a real transition the store can detect by comparing against the previously-stored row), while `locked_at` is in a stricter `neverSent` set: TimelyKit sends it in **no** circumstance. Android was never affected; it never sends the key at all.
  - **A gap that WAS real when this section was first written, since closed - stated in the past tense on purpose so this doesn't become another stale note.** `guard_locked`'s admin lock-clear escape hatch originally had **no `base_revision` check**, unlike `guard_reopen`, which did - so a stale admin client could clear an approval lock the same way an ordinary title edit could accidentally clear one. Task #25 fixed this (re-verified directly in this pass): `guard_locked` now also requires `current_base? = existing != nil and mutation["base_revision"] == existing.server_revision`, matching `guard_reopen`'s protection exactly. The client-side reasoning below (why `locked_at` stays `neverSent` regardless) is now over-determined rather than load-bearing on this specific gap - it still holds for the *other* reason.
  - **Client-side guards do not protect against this, and this matters generally, not just here.** iOS has five `guard !span.isLocked` checks (verified: `SpanCorrection.swift`, 5 call sites), but they read the **local, possibly-stale** copy of the span. They stop a user from *deliberately* editing a span their own client believes is locked; they do nothing when the client's local copy simply hasn't learned about a lock another device just applied — which is exactly the accidental case that matters, and an offline-first client is the one most likely to be holding a stale copy at the exact moment it matters.
  - **Consequence, deliberately accepted, not an oversight**: because Android never sends `locked_at` and TimelyKit now refuses to in any form, **the admin unlock flow (US-068, "reopen approved report") is not expressible from either companion app** — an admin must use macOS or web to clear a billing-approval lock. This is the right default regardless of the server-side fix above: clearing a billing lock shouldn't be something that falls out of editing a title by accident, which is precisely how the bug happened in the first place. Enabling it later on a companion means adding a real lock/unlock UI affordance that threads an explicit intent flag through to the wire layer — not loosening the `neverSent` set or inferring intent from a nil. Cross-referencing US-068 here so whoever picks up that story finds this constraint rather than rediscovering it. Ordinary edits to a locked day still fall through correctly today: they hit `guard_locked`'s rejection path and surface as `locked_day` ("The day was approved and locked before this edit reached the server").

**Triage note for the first live SSO attempt, because this flow has never run end to end and the first failure someone sees is likely to be `state_mismatch`.** That single error code has **three distinct causes that present identically**, and they need different fixes:
1. **The 900s session cookie expired mid-flow** — fails only on SLOW logins (password + a 2FA code typed on a phone). This was a real, already-fixed bug: `max_age` was 300s, raised to 900s (see "TWO PRE-EXISTING SECURITY GAPS" above) — but 900s is still finite, and a slow enough login can still outrun it.
2. **The session cookie was dropped entirely, not expired** — e.g. it doesn't survive round-tripping through `ASWebAuthenticationSession`. Fails on EVERY attempt, including a fast re-login against a provider session that's still live.
3. **A genuine CSRF trip** — the failure mode the check exists to catch, and the one case you'd hope to see essentially never in practice.

**The distinguisher, which is the part worth writing down**: *if it fails 100% of the time, including on a fast re-login, suspect the cookie isn't surviving the round trip — not the timeout.* An expired cookie can only fail slow flows; by definition it can't explain a fast one failing too. A dropped cookie fails all of them, fast or slow. Checking the timeout first when every attempt fails, including fast ones, wastes the obvious hour before the real cause gets attention.
