# Marcus Lee — Newly-Onboarding Engineer

## Demographics

| Field | Value |
|-------|-------|
| **Age** | 24-30 |
| **Role** | Mid-level Backend Engineer (new hire) |
| **Technical Level** | Intermediate |
| **Industry** | Fintech |
| **Location** | Hybrid, London |

## Bio

Marcus just joined a team with a sprawling codebase and a README that stops at "run `make up`." He's spent his first two weeks ctrl-clicking through files trying to build a mental map. He learns spatially and remembers *where* things are better than what they're named.

## Goals

1. Build an accurate mental model of an unfamiliar codebase fast
2. Find where a given feature actually lives and what it touches
3. Stop pestering senior engineers with "where does X happen" questions

## Frustrations

1. File trees and search hide the shape of the system
2. Onboarding docs are thin, outdated, or nonexistent
3. He can't tell which modules are core and which are peripheral

## Behaviors

- Heavy IDE "go to definition" and grep user
- Draws his own ad-hoc diagrams on paper to orient himself
- Asks in Slack as a last resort, feels like a burden

## Job to Be Done

> "When I'm dropped into a new codebase, I want to fly through its real structure and drill into the part I'm assigned, so I can become productive without weeks of blind spelunking."

## Relationship to Product

Marcus is the onboarding wedge — the first-run "import a repo and explore it" path is made for him. He values legible labels, focus-on-selection, and a gentle first-run experience. He churns if the empty state confuses him or labels are unreadable when zoomed out.

## Scenarios

1. **First-day map** — Marcus imports the repo and slowly orbits the whole system to see its major clusters before touching any code.
2. **Ticket scoping** — Assigned a bug, he searches for the class by name, focuses it, and traces its callers to scope the blast radius.
