# Zellij Plugin API Reference

> **Verified against Zellij `0.45.0`** (workspace `Cargo.toml:85`).
> The plugin API is **version-specific and moves fast**. Every signature below was read from
> the checkout, not recalled. Before writing code against a *different* checkout, re-read the
> cited files — variants are added and renamed between releases.

## The Execution Model

A Zellij plugin is a **WASM module** compiled to `wasm32-wasip1`, loaded by the server's plugin
thread. It is not a library the host links — it is a guest module with exported C-ABI functions
that the host calls, and imported host functions it calls back into.

```
┌──────────────────────────────┐
│ zellij-server plugin thread  │
│                              │
│   calls guest exports:       │      ┌─────────────────────────┐
│     load() ─────────────────────────▶ your plugin (.wasm)     │
│     update() -> bool ───────────────▶                         │
│     pipe()   -> bool ───────────────▶  #[derive(Default)]     │
│     render(rows, cols) ─────────────▶  struct State           │
│                              │      │                         │
│   serves host imports:       │◀─────── shim::* (202 fns)      │
│     subscribe, open_file...  │      └─────────────────────────┘
└──────────────────────────────┘
```

**Data crosses the boundary as protobuf over stdin/stdout.** `register_plugin!` generates the
exports, which read protobuf bytes from stdin, decode, and hand you typed Rust values. You never
write this yourself, but knowing it explains the failure mode below.

> **The version-mismatch failure.** Because both sides encode/decode protobuf, a plugin built
> against one Zellij version and run on another panics on decode rather than failing gracefully.
> The runtime message for this is `PLUGIN_MISMATCH` (`zellij-tile/src/lib.rs:72-82`). If a
> self-compiled plugin panics on load, **rebuild the plugin against the running Zellij** before
> debugging your own code.

## The `ZellijPlugin` Trait

`zellij-tile/src/lib.rs:32-49`. Every method has a default, so implement only what you use.
The trait requires `Default` — that is how the host constructs your state.

```rust
pub trait ZellijPlugin: Default {
    /// Called once when the plugin loads. Subscribe to events and request permissions here.
    /// `configuration` is the key/value map from the layout/config `plugin` node.
    fn load(&mut self, configuration: BTreeMap<String, String>) {}

    /// Called for each Event you subscribed to.
    /// Return `true` to tell Zellij to re-render (it will then call `render`).
    fn update(&mut self, event: Event) -> bool { false }

    /// Called when data is piped to the plugin.
    /// A `payload` of `None` signifies the pipe has ended.
    /// Return `true` to request a re-render.
    fn pipe(&mut self, pipe_message: PipeMessage) -> bool { false }

    /// Called after an update/pipe that returned true, and whenever Zellij otherwise needs a
    /// repaint (startup, resize).
    /// `rows`/`cols` are the CONTENT size — excluding the frame if pane frames are enabled.
    fn render(&mut self, rows: usize, cols: usize) {}
}
```

**Four things that bite people:**

1. **`update`/`pipe` returning `true` is the *only* way to request a render.** Returning `false`
   from an event that changed your state means the change is invisible until something else
   triggers a repaint. When state changed, return `true`.
2. **Don't render from `update`.** Print inside `render` only. `update` decides *whether* to render.
3. **`render`'s `rows`/`cols` exclude the frame.** Don't subtract for the border yourself.
4. **You are re-rendered on resize with no `update`.** `render` must be a pure function of your
   state — never accumulate output across calls.

### Registration

`register_plugin!(State)` (`zellij-tile/src/lib.rs:100-172`) generates `load`/`update`/`pipe`/
`render`/`plugin_version` exports plus a `main()` that installs a panic hook forwarding to
`report_panic`. Your state lives in a `thread_local!` `RefCell`.

```rust
use zellij_tile::prelude::*;

#[derive(Default)]
struct State { /* ... */ }

impl ZellijPlugin for State { /* ... */ }

register_plugin!(State);
```

> Because state is a `thread_local! RefCell` borrowed across each host call, **never hold a
> `RefCell` borrow across a shim call that re-enters your plugin**. In practice: keep `&mut self`
> work self-contained; don't stash borrows in globals.

## Events

`Event` is defined at `zellij-utils/src/data.rs:945` and marked `#[non_exhaustive]` —
**always include a `_ => {}` arm** in your match, or your plugin breaks on the next Zellij release.

> **Non-obvious and important:** `EventType` is **not a hand-written enum**. It is generated by
> `strum` as the discriminant of `Event`:
> ```rust
> #[derive(EnumDiscriminants, ...)]
> #[strum_discriminants(name(EventType))]   // data.rs:943
> pub enum Event { ... }
> ```
> You **subscribe** with `EventType` (the fieldless discriminant) and **receive** an `Event`
> (the payload-carrying variant). Adding an event upstream means adding a variant to `Event` —
> `EventType` follows automatically. The same pattern applies to `Permission`/`PermissionType`.

### Subscribing

`zellij-tile/src/shim.rs:53` / `:62`.

```rust
fn load(&mut self, _config: BTreeMap<String, String>) {
    subscribe(&[EventType::ModeUpdate, EventType::TabUpdate, EventType::Key]);
}
fn update(&mut self, event: Event) -> bool {
    match event {
        Event::TabUpdate(tabs) => { self.tabs = tabs; true }   // changed → render
        Event::Key(_) => false,                                 // no visible change
        _ => false,                                             // REQUIRED: non_exhaustive
    }
}
```

> **Subscribe narrowly.** Every subscribed event is a protobuf encode + WASM call. `InputReceived`
> and `Mouse` (especially `Hover`) fire at high frequency; subscribing to them "just in case" is a
> measurable performance cost on every keystroke across the whole session.

Two events are performance-relevant in the other direction:
- `InitialKeybinds(KeybindsVec)` — sent once on load and on reconfiguration. Subscribing to it
  *signals to Zellij that you cache keybinds*, so it may send lighter `ModeUpdate` events without
  keybind payloads (`data.rs`, `InitialKeybinds` doc comment). Status-bar-like plugins want this.

### The permission flow

Permissions are **asynchronous and user-gated**. `request_permission` returns immediately; the
answer arrives later as an event.

```rust
fn load(&mut self, _config: BTreeMap<String, String>) {
    request_permission(&[
        PermissionType::ReadApplicationState,
        PermissionType::ChangeApplicationState,
    ]);
    subscribe(&[EventType::PermissionRequestResult, EventType::TabUpdate]);
}

fn update(&mut self, event: Event) -> bool {
    match event {
        Event::PermissionRequestResult(status) => {
            self.granted = matches!(status, PermissionStatus::Granted);
            true
        },
        _ => false,
    }
}
```

> **The classic bug:** calling a privileged shim function in `load()` immediately after
> `request_permission`. The grant has not happened yet — the user hasn't answered the prompt.
> Gate privileged work on `PermissionRequestResult`, not on `load` completing.
>
> Permissions are cached per-plugin after the first grant, so this bug is **invisible on every run
> after the first**. Test with a cleared plugin permission cache.

## Configuration

`load()` receives `BTreeMap<String, String>` decoded from `ProtobufPluginConfiguration`
(`zellij-tile/src/lib.rs:119-126`). It comes from the `plugin` node's KDL children:

```kdl
pane {
    plugin location="file:/path/to/my-plugin.wasm" {
        some_key "some_value"
        another  "42"
    }
}
```
→ `{"some_key": "some_value", "another": "42"}`

All values are strings — parse and validate yourself, with sane defaults. Config can change at
runtime; subscribe to `PluginConfigurationChanged` if you want to react.

## Pipes

`PipeMessage` / `PipeSource` at `zellij-utils/src/data.rs:2995-3010`.

```rust
pub enum PipeSource {
    Cli(String),   // the pipe_id of the CLI pipe (used for blocking/unblocking)
    Plugin(u32),   // the originating plugin id
    Keybind,
}

pub struct PipeMessage {
    pub source: PipeSource,
    pub name: String,
    pub payload: Option<String>,   // None => the pipe has ENDED
    pub args: BTreeMap<String, String>,
    pub is_private: bool,
}
```

Three sources: `zellij pipe` from the CLI, another plugin via `pipe_message_to_plugin`, or a
keybind bound to a pipe action.

> **`pipe()`'s `bool` is a render request, exactly like `update()`'s — it is _not_ "I handled
> this" and it does _not_ block the pipe.** Blocking is separate and explicit:
> `block_cli_pipe_input` / `unblock_cli_pipe_input` (shim), keyed by the `pipe_id` in
> `PipeSource::Cli(String)`. Confusing these means either a CLI caller that hangs forever or one
> that returns before your work is done.

Output back to a CLI pipe goes through `cli_pipe_output`.

`is_private` distinguishes a message addressed specifically to this plugin from a broadcast.

## Workers

Workers run long tasks off the plugin's render path. `ZellijWorker` at `zellij-tile/src/lib.rs:66-70`:

```rust
pub trait ZellijWorker<'de>: Default + Serialize + Deserialize<'de> {
    fn on_message(&mut self, message: String, payload: String) {}
}
```

Registration takes three arguments (`lib.rs:197`):

```rust
register_worker!(
    FileSearchWorker,   // the type
    file_search_worker, // export name → registers the namespace "file_search"
    FILE_SEARCH_WORKER  // static holding worker state
);
```

> The naming is load-bearing: an export named `file_search_worker` registers the namespace
> **`file_search`** (the `_worker` suffix is stripped). You address it as `"file_search"` from
> `post_message_to`.

**Round trip:**
1. Plugin → worker: `post_message_to(PluginMessage { worker_name, name, payload })`
2. Worker → plugin: `post_message_to_plugin(...)`
3. Plugin receives `Event::CustomMessage(name, payload)` — **you must `subscribe` to
   `EventType::CustomMessage` first**, or the reply vanishes silently (`lib.rs:60-64`).

Messages are `String`/`String`, so serialize structured data (serde_json) yourself. Worker state
must be `Serialize + Deserialize`.

### Sync vs async

Most shim calls are **fire-and-forget** — they send an instruction to the server and return.
A few **block and return data**: `get_pane_info`, `get_tab_info`, `get_plugin_ids`,
`get_zellij_version`, `get_focused_pane_info`, `dump_layout`, `get_pane_scrollback`,
`get_session_list`, `get_pane_cwd`, `get_pane_pid`, `generate_random_name`.

Others are async-with-callback: `run_command` returns nothing and later delivers
`Event::RunCommandResult`; `web_request` → `Event::WebRequestResult`. Subscribe to the result
event or the reply is dropped.

The `Context` (`BTreeMap<String, String>`) parameter on `run_command`/`web_request`/`open_file` is
**echoed back in the result event**. Use it to correlate replies with requests — there is no
request id, so with concurrent commands in flight, context is the *only* way to tell results apart.

## UI Components

`zellij-tile/src/ui_components/` — `text.rs`, `table.rs`, `nested_list.rs`, `ribbon.rs`.

These render via a **serialized escape protocol** the host interprets, so the styling follows the
user's theme automatically. Prefer them over hand-rolled ANSI: hardcoded colors ignore the theme.

### `Text` (`text.rs:5`)

A builder. Styling methods come in `_indices` / `_range` / `_substring` / `_all` families:

```rust
let t = Text::new("my label")
    .selected()                  // themed selection styling
    .opaque()
    .color_range(0, 0..2)        // color "index level" 0 over a range
    .dim_substring("label")
    .error_color_all();

print_text(t);
print_text_with_coordinates(t, x, y, Some(width), Some(height));
```

Also: `dim_indices/range/substring/all`, `unbold_*`, `error_color_*` (incl. `_nth_substring`,
`_last_substring`), `success_color_*`, `color_indices/range/substring/nth_substring/last_substring/all`,
`content()`, `len()`, `serialize()`.

> `color_*` takes an **index level** (`usize`), not an RGB value — it selects a themed color slot.
> That indirection is why these components respect the user's theme.

### `Table` (`table.rs:5`)

```rust
let table = Table::new()
    .add_row(vec!["NAME", "STATUS"])         // plain strings
    .add_styled_row(vec![Text::new("web").selected(), Text::new("up")]);
print_table(table);
print_table_with_coordinates(table, x, y, Some(width), Some(height));
```

First row is treated as the header.

### `ribbon` (`ribbon.rs`) and `nested_list`

`print_ribbon`, `print_ribbon_with_coordinates`, `serialize_ribbon_line(_with_coordinates)` —
the tab-bar/status-bar style ribbon. `nested_list` renders indented trees.

Each component has a `serialize_*` counterpart when you need to compose output rather than print
it directly.

## Building and Loading

**Target: `wasm32-wasip1`** (`xtask/src/build.rs:46`, `:189`).

> This is a version-sensitive detail. Older documentation and blog posts say `wasm32-wasi`; this
> checkout builds `wasm32-wasip1`. Using the wrong target is a common first-run failure.

```bash
rustup target add wasm32-wasip1
cargo build --target wasm32-wasip1            # debug
cargo build --release --target wasm32-wasip1
# artifact: target/wasm32-wasip1/{debug,release}/<crate-name>.wasm
```

For in-repo plugins, prefer the workspace task runner: `cargo xtask build` (see
`references/core/testing-and-build.md`).

### Loading a plugin

```kdl
// From a file (absolute path, or relative to the layout's dir)
pane {
    plugin location="file:/home/me/plugins/my-plugin.wasm"
}

// A builtin
pane {
    plugin location="zellij:status-bar"
}

// A remote plugin
pane {
    plugin location="https://example.com/my-plugin.wasm"
}

// Via an alias declared in config.kdl `plugins { ... }`
pane {
    plugin location="my-alias"
}
```

Also loadable ad hoc from the CLI:
```bash
zellij plugin -- file:/abs/path/to/my-plugin.wasm
zellij plugin --floating -- file:/abs/path/to/my-plugin.wasm
```

### The dev loop

The friction here is real: an edit requires rebuild + reload.

1. `cargo build --target wasm32-wasip1`
2. Reload in the live session — bind or invoke the `start_or_reload_plugin` path rather than
   restarting Zellij.

> **Zellij caches plugins.** A rebuilt `.wasm` at the same path may not be picked up. If your
> change appears to have no effect, suspect the cache before your code — reload the plugin
> explicitly, or start Zellij with the plugin cache bypassed.

Plugins cannot print to a terminal for debugging — stdout *is* the render channel. Use the
`report_panic` hook (installed automatically) and Zellij's log file rather than `println!`
debugging. `eprintln!`/`log` output lands in the Zellij log, not your pane.

## Checklist

- [ ] `#[derive(Default)]` on state; `register_plugin!` called
- [ ] `_ => {}` arm present in the `Event` match (`#[non_exhaustive]`)
- [ ] Permissions requested in `load`, privileged work gated on `PermissionRequestResult`
- [ ] Tested with a **cleared permission cache** (first-run path)
- [ ] Subscribed only to events actually consumed (no idle `Mouse`/`InputReceived`)
- [ ] `update`/`pipe` return `true` exactly when state changed
- [ ] `render` is a pure function of state; correct at 80×24 and after resize
- [ ] `CustomMessage` subscribed if workers are used
- [ ] Async results correlated via `Context`, not assumed ordering
- [ ] Built for `wasm32-wasip1` against the **running** Zellij version
- [ ] UI built from `ui_components` (theme-aware), not hardcoded ANSI
