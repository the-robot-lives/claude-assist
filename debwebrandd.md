# Packaging & Distributing Personal Rust + Shell Dev Tools as .deb / .rpm / Homebrew

## TL;DR
- **Stop vendoring via git subtrees; adopt nfpm + GoReleaser-style GitHub Actions + a self-hosted static apt/rpm repo (or Cloudsmith's free OSS tier) + a personal Homebrew tap.** This gives one YAML per tool that emits both .deb and .rpm, tag-triggered CI, and `apt`/`dnf`/`brew` installs without begging for upstream acceptance.
- **Do not bet on official registries for small personal tools.** homebrew-core requires ≥30 forks OR ≥30 watchers OR ≥75 stars — and **3× that (≥90 forks, ≥90 watchers, or ≥225 stars) for self-submitted software**; Debian requires an ITP bug + a Debian Developer sponsor; Fedora requires a formal package review. All are high-effort and gated on notability. Use a personal tap, Fedora COPR, and OpenSUSE Build Service (OBS) as the realistic "official-ish" channels.
- **cargo-dist is no longer a safe long-term bet** — its vendor (axo.dev) wound down commercially in 2025 and the tool is now maintained by essentially one ex-employee plus a semi-official Astral fork. Prefer the language-agnostic GoReleaser + nfpm stack, which handles both your Rust binaries and pure-shell tools from one pipeline.

## Key Findings
1. **One tool covers most of your Linux packaging: nfpm.** It's a single static Go binary (no Ruby, unlike fpm) that builds deb, rpm, apk, ipk and Arch packages from one `nfpm.yaml`. It handles both compiled Rust binaries and pure-shell scripts identically — you just point `contents:` at files.
2. **For Rust binaries, build a cross-compilation matrix** targeting `x86_64/aarch64-unknown-linux-{gnu,musl}` and `x86_64/aarch64-apple-darwin`. Use `musl` for fully static Linux binaries, and `cargo-zigbuild` or `cross` for painless cross-compilation. Publish to crates.io as a bonus channel (`cargo install`).
3. **homebrew-core acceptance is gated on notability**; a personal tap (`homebrew-<name>` repo) has no such bar and is the correct home for personal tools. Formulas can download pre-built binaries from GitHub Releases (simplest) or ship bottles.
4. **Self-hosted repos are cheap and low-maintenance if static:** an apt repo can be a set of files on object storage / GitHub Pages generated by `aptly` or `reprepro`; an rpm repo is just `createrepo_c` output + GPG-signed metadata. Both served by nginx or any static host.
5. **Modern apt key management uses `signed-by=` + a keyring in `/usr/share/keyrings` — never `apt-key`.** rpm repos sign metadata with a GPG key referenced in the `.repo` file.
6. **Hosted alternatives (Cloudsmith, packagecloud, Gemfury) have free OSS tiers** that eliminate all repo-hosting toil at the cost of lock-in. Cloudsmith's free open-source tier (50 GB storage for OSS projects) is the most generous.
7. **CI/CD: GoReleaser on `git tag` builds artifacts, runs nfpm, signs, publishes GitHub Releases, and updates your Homebrew tap automatically.** Changelogs via git-cliff (Rust, single binary, conventional commits) or release-please (PR-based).

## Details

### 1. Project preparation (repo hygiene → adoption)
Get each tool's repo into a state maintainers and users expect:
- **README** with a clear one-line description, install instructions per channel, and usage. homebrew-core, Debian, and Fedora all effectively require a homepage.
- **LICENSE**: pick an OSI-approved permissive license. Rust convention is dual `MIT OR Apache-2.0` (matches the Rust compiler itself); put the SPDX identifier in `Cargo.toml`'s `license` field. Debian/Fedora both require the license to be clearly stated and DFSG/Fedora-allowed; reviewers check for embedded code with incompatible licenses, not just the LICENSE file.
- **Semantic versioning** with git tags (`vMAJOR.MINOR.PATCH`). Tarballs for homebrew-core must carry the version in the filename and come from a tagged stable release — Homebrew won't accept untagged/rolling sources because it can't build bottles for them.
- **CHANGELOG.md** following Keep a Changelog, ideally auto-generated (see §9).
- **Man pages** (`man1/tool.1`) and **shell completions** (bash/zsh/fish) — ship these in your packages; they're a mark of a "real" tool and are expected by Debian.
- **Reproducible builds & signing**: tag releases, build in CI from the tag, and sign artifacts. Modern approach: GitHub Artifact Attestations (`gh attestation verify`) and/or cosign signing of checksums, plus GPG-signing the repo metadata.

### 2. Rust-specific packaging
**Targets** (the ones that matter):
```
x86_64-unknown-linux-gnu     # standard glibc Linux
x86_64-unknown-linux-musl    # fully static Linux
aarch64-unknown-linux-gnu    # ARM servers (Graviton/Ampere)
aarch64-unknown-linux-musl   # static ARM Linux
x86_64-apple-darwin          # Intel macOS
aarch64-apple-darwin         # Apple Silicon
```
**Static musl build:**
```
rustup target add x86_64-unknown-linux-musl
sudo apt install musl-tools     # musl-gcc
cargo build --release --target x86_64-unknown-linux-musl
file target/.../tool            # → statically linked
ldd  target/.../tool            # → not a dynamic executable
```
**Cross-compilation options:**
- `cross` — drop-in cargo replacement, runs builds in Docker with toolchains + QEMU preinstalled. Best when you have C deps: `cross build --release --target aarch64-unknown-linux-gnu`.
- `cargo-zigbuild` — uses Zig as linker/C toolchain; trivially cross-compiles glibc (with pinned versions like `aarch64-unknown-linux-gnu.2.17`), musl, and macOS `universal2` (`cargo zigbuild --target universal2-apple-darwin`). Simplest when you have few/no complex C deps; note it uses `zig cc -nostdinc`, so projects with system C headers may need `CFLAGS='-isystem /usr/include'`.

**Release profile** for small static binaries in `Cargo.toml`:
```toml
[profile.release]
lto = true
codegen-units = 1
panic = "abort"
strip = true
```
**Cargo-native packagers** (alternative to nfpm if you want everything in `Cargo.toml`):
- `cargo-deb` — reads `[package.metadata.deb]`, e.g. `assets = [["target/release/tool","usr/bin/","755"]]`.
- `cargo-generate-rpm` — reads `[package.metadata.generate-rpm]`; output lands in `target/generate-rpm/`. (`cargo-rpm`/`cargo rpm` is **end-of-life since 2022** — do not use it; its own README points you to cargo-generate-rpm.)

**crates.io** as an extra channel: `cargo publish`. Lets Rust users `cargo install tool`. Good for discoverability but requires the user to have a Rust toolchain and compiles from source — not a substitute for system packages.

**cargo-dist caveat (important):** cargo-dist ("dist") automates the whole Rust release matrix, but its vendor axo.dev has wound down commercially. Its "Axo Releases" hosting was removed in dist v0.29.0 (2025-07-31 — the CHANGELOG states "0.29.0 includes all of the new features from Astral's fork of dist along with some new bugfixes. It also removes support for Axo Releases."), the original author (Aria "Gankra" Beingessner) moved to Astral, and the axo.dev commercial site is now parked/for-sale. The tool is still maintained (latest **v0.32.0, 2026-05-21**) but by essentially one former employee (Misty De Méo) plus community PRs, with issue creation restricted. Astral maintains "an unofficial fork of axodotdev/cargo-dist 0.28.0 to apply minor updates and fixes for astral's projects" (per posit-dev/air #297) but has *not* officially taken over stewardship. Since you also have pure-shell tools (which cargo-dist doesn't handle), prefer GoReleaser+nfpm.

### 3. Shell-script packaging (no compilation)
Pure-shell tools package identically — there's nothing to compile, you just place files at FHS paths. **FHS layout (per FHS 3.0):**
- `/usr/bin/tool` — user-facing executables (0755). **No subdirectories allowed in `/usr/bin`.**
- `/usr/libexec/tool/` **or** `/usr/lib/tool/` — internal helper scripts *not* meant to be run directly by users. FHS 3.0 explicitly permits either, but a package must pick one, not both. Good place for sub-scripts a shell tool sources.
- `/usr/share/man/man1/tool.1` — man pages (gzipped by convention in deb/rpm).
- Completions: `/usr/share/bash-completion/completions/tool`, `/usr/share/zsh/vendor-completions/_tool`, `/usr/share/fish/vendor_completions.d/tool.fish`.
- `/etc/tool/` — config, marked `config|noreplace` so upgrades don't clobber user edits.

**fpm vs nfpm:** fpm (Ruby) is more featureful but drags in a Ruby runtime + tar. nfpm is a single static binary, one YAML → all formats, ideal for CI. **Recommendation: nfpm** for both shell and Rust tools. (Tip from nfpm's own docs: run `lintian` against generated debs, and ship a `.lintian-overrides` file to silence expected warnings.)

### 4. Debian packaging
Two philosophies:
- **The "proper" `debian/` directory** (`debian/control`, `rules`, `changelog`, `copyright`, `compat`) — required if you ever want the package in *official Debian*. Validate with **`lintian`** (Debian's package linter; sponsors run it and expect it clean). This is the heavyweight path.
- **The pragmatic path** (nfpm / fpm / cargo-deb) — generates a working `.deb` from metadata without a full `debian/` tree. Correct for self-hosted/PPA distribution; *not* accepted into official Debian.

**Path to official Debian (realistic assessment — high effort):**
1. File an **ITP** ("Intent to Package") bug against the `wnpp` pseudo-package.
2. Build a policy-compliant source package; test; run lintian.
3. Upload to **mentors.debian.net**, enable "Needs a sponsor".
4. File an **RFS** (Request For Sponsorship) bug against the `sponsorship-requests` pseudo-package (subject like `RFS: tool/1.0-1 [ITP] -- description`).
5. A **Debian Developer** reviews and uploads for you. After several sponsored uploads you may become a Debian Maintainer (limited upload rights), then optionally a Debian Developer.

The Debian docs are blunt: "Debian is a distribution, not a general purpose repository… Please do not treat Debian as a platform to advertise your own software, unless there is some real request for it." For a personal tool with few users this will likely stall. **Realistic alternatives:** Launchpad PPA (Ubuntu), self-hosted apt repo (§7), or OpenSUSE Build Service (§5), which builds deb *and* rpm for many distros from one place.

### 5. RPM packaging
- **spec file + `rpmbuild`**: classic approach. Key sections: `%build`, `%install`, `%files` (must list every shipped file exactly — COPR/rpmbuild fail otherwise), `%changelog`. `Requires` = runtime deps; `BuildRequires` = build-chroot deps. Build in a clean chroot with **`mock`** to catch missing BuildRequires.
- **Fedora COPR** — the *easy* path. Community build service (a PPA/AUR analogue for RPM). Upload a spec or wire a Git webhook; it builds for chosen chroots (Fedora releases, RHEL/EPEL via `rhel-8`/`rhel-9`, across x86_64/aarch64/etc.) and serves a GPG-signed repo — all packages auto-signed with the repo key, verified by DNF. COPR is commonly used as a staging ground before official Fedora and can run the `fedora-review` tool automatically after each build.
- **Official Fedora inclusion** — requires a formal **package review**: another maintainer reviews your spec against Fedora guidelines (a mandatory `fedora-review` check). Higher effort than COPR, gated on a reviewer's time.
- **OpenSUSE Build Service (OBS)** — builds RPMs for openSUSE, SLES, Fedora, RHEL/CentOS, Mandriva/Mageia **and** debs for Debian/Ubuntu from a single source, for multiple architectures. The single best "build once, target many distros" service; supports per-distro spec/dsc variants (`tool-Fedora_Extras_6.spec`, `projectName-repository.dsc`) and can link/aggregate dependencies from other OBS projects. Used in production by Collabora (deb for Debian/Ubuntu/Apertis), Datto (25+ targets), Linaro, and others.

### 6. Homebrew
**Personal tap (the right choice for personal tools):**
- Create a GitHub repo named `homebrew-<name>` (the `homebrew-` prefix is implicit in `brew tap`). Users run `brew tap you/<name> && brew install tool`, resolving to `github.com/you/homebrew-<name>`.
- Put formulas in `Formula/tool.rb`. A minimal binary formula:
```ruby
class Tool < Formula
  desc "One-line description"
  homepage "https://github.com/you/tool"
  version "1.2.3"
  license "MIT"

  on_macos do
    on_arm do
      url "https://github.com/you/tool/releases/download/v1.2.3/tool-1.2.3-aarch64-apple-darwin.tar.gz"
      sha256 "..."
    end
    on_intel do
      url ".../tool-1.2.3-x86_64-apple-darwin.tar.gz"
      sha256 "..."
    end
  end

  on_linux do
    on_intel do
      url ".../tool-1.2.3-x86_64-unknown-linux-musl.tar.gz"
      sha256 "..."
    end
    on_arm do
      url ".../tool-1.2.3-aarch64-unknown-linux-musl.tar.gz"
      sha256 "..."
    end
  end

  def install
    bin.install "tool"
    man1.install "tool.1"
    bash_completion.install "completions/tool.bash" => "tool"
    zsh_completion.install "completions/_tool"
    fish_completion.install "completions/tool.fish"
  end

  test do
    system "#{bin}/tool", "--version"
  end
end
```
- **Bottles** (Homebrew's pre-built binary format, `bottle do … end` with per-OS sha256s) are optional for a tap; downloading pre-built release tarballs directly (as above) is simpler to automate. Bottles add value by letting users fall back to `--build-from-source`, but they're a two-step publish (build formula, then `brew bottle`). For a personal tap, the direct-download style is the pragmatic default.
- `brew create --rust <url>` scaffolds a formula. Validate with **`brew audit --strict --online tool`** and **`brew test tool`** before publishing.

**homebrew-core acceptance (realistic bar):** must be a stable tagged release; build/test on the 3 latest macOS versions (Apple Silicon + Intel) and x86_64 Linux; and per the official docs (`docs.brew.sh/Acceptable-Formulae`): *"be known (e.g. GitHub repositories should have >=30 forks, >=30 watchers or >=75 stars) notability requirements for self-submitted software are 3 times higher than the applicable thresholds above (e.g. on GitHub: >=90 forks, >=90 watchers, or >=225 stars)"*, and it should be used by someone other than the author. Homebrew is explicit this is a maintenance-burden filter, not a quality judgment: *"Please note that this has nothing to do with the quality of the software. It's just that there are already thousands of formulae at homebrew/core, and we can't unconditionally accept anything. So, we have to draw a line somewhere."* For personal tools: stay in your tap until/unless real popularity appears.

### 7. Self-hosted repository infrastructure
**apt repo:**
- **`aptly`** — snapshots, multiple versions per package, S3/object-storage publishing, REST API. Preferred for anything nontrivial. Core flow: `aptly repo create`, `aptly repo add`, `aptly snapshot create`, `aptly publish snapshot`.
- **`reprepro`** — simpler, one version per package, multi-distro/component; good middle ground. `reprepro -b /var/packages includedeb bookworm tool_1.0_amd64.deb`.
- **`deb-s3`** — dead-simple uploads straight into an S3-hosted apt repo (`deb-s3 upload --bucket ex --codename stable tool.deb`).
- Or fully static: generate the tree with `aptly`/`apt-ftparchive` and serve from GitHub Pages / object storage behind nginx.

**rpm repo:** run **`createrepo_c`** over a directory of RPMs to generate `repodata/`, GPG-sign metadata (`gpg --detach-sign --armor repodata/repomd.xml`) and the RPMs themselves (`rpm --addsign`), then serve statically.

**GPG key management:** generate a dedicated repo-signing key, keep the private key in CI secrets only, publish the public key over HTTPS. Sign apt `Release` (→ `InRelease`/`Release.gpg`) and rpm `repomd.xml`. Rotate on a schedule and publish the new key before switching.

**How users add the repo (modern, `signed-by`):**
```bash
# apt (Debian/Ubuntu) — NEVER apt-key
curl -fsSL https://repo.example.com/gpg.key \
  | sudo gpg --dearmor -o /usr/share/keyrings/example-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/example-archive-keyring.gpg] https://repo.example.com/apt stable main" \
  | sudo tee /etc/apt/sources.list.d/example.list
sudo apt update && sudo apt install tool
```
```ini
# dnf/yum — /etc/yum.repos.d/example.repo
[example]
name=Example
baseurl=https://repo.example.com/rpm/
enabled=1
gpgcheck=1
gpgkey=https://repo.example.com/gpg.key
```
`apt-key` is deprecated (removed in Ubuntu 24.04+); global keyrings (`/etc/apt/trusted.gpg`, `trusted.gpg.d/`) let any key sign for any repo — the exact vulnerability `signed-by` closes. Use `/usr/share/keyrings` (package-managed) or `/etc/apt/keyrings` (admin-managed, APT ≥ 2.4). Name keys `<repo>-archive-keyring.gpg` per the Debian wiki convention.

### 8. Hosted alternatives
- **Cloudsmith** — 28+ formats incl. deb/rpm/Homebrew/cargo, global CDN, free **open-source** tier (50 GB storage for OSS projects — the most generous of the three). Paid tiers use usage-based storage+bandwidth pricing that can spike: per CloudRepo's 2026 breakdown, *"If you exceed your plan's included storage or delivery limits, you pay on-demand overage fees at $1.50 per GB for both storage and delivery. This rate applies to the Pro plan"* (Pro is ~$149/mo with 5 GB storage / 25 GB delivery). Best hosted option for OSS.
- **packagecloud.io** — deb/rpm/gem/etc., fixed monthly pricing by repo count; simple `apt-get`/`yum` install UX.
- **Gemfury** — private + public packages, per-package pricing.
- **GitHub Releases + install script** — zero-cost, generous download bandwidth; pair with a `curl … | sh` installer and/or a Homebrew tap. Simplest of all; no native apt/dnf integration though.

**Tradeoff:** hosted = near-zero maintenance, someone else's uptime/pricing, mild lock-in. Self-hosted static = full control, near-zero cost, but you own key rotation, metadata correctness, and uptime.

### 9. CI/CD release automation
**GoReleaser** is the recommended orchestrator (language-agnostic; handles your shell tools and, via a build step, your Rust binaries). On `git tag` it: builds the matrix, runs **nfpm** to emit deb/rpm, creates the GitHub Release with artifacts + checksums, signs (cosign/GPG), and **commits an updated formula to your Homebrew tap**.

Minimal workflow:
```yaml
name: release
on:
  push:
    tags: ["v*"]
permissions:
  contents: write
jobs:
  goreleaser:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }        # required for changelog
      - uses: actions/setup-go@v5
      - name: Import GPG
        id: import_gpg
        uses: crazy-max/ghaction-import-gpg@v6
        with:
          gpg_private_key: ${{ secrets.GPG_PRIVATE_KEY }}
          passphrase: ${{ secrets.PASSPHRASE }}
      - uses: goreleaser/goreleaser-action@v7
        with: { version: "~> v2", args: "release --clean" }
        env:
          GITHUB_TOKEN: ${{ secrets.GH_PAT }}   # PAT with write to the tap repo
          GPG_FINGERPRINT: ${{ steps.import_gpg.outputs.fingerprint }}
```
Pushing the tap to a *separate* repo requires a **PAT with `repo` write** (the default `GITHUB_TOKEN` can't cross repos) — store it as `GH_PAT`.

**Changelogs:** **git-cliff** (Rust binary, parses Conventional Commits, Tera templates, `git cliff --latest` in the release job, `cliff.toml` config) or **release-please** (Google; maintains a "Release PR" whose merge bumps version + tags + creates the release). git-cliff suits a binary-first, no-Node toolchain and is itself trivially installable (`brew install git-cliff` / `cargo install git-cliff`).

**Rust matrix note:** for the compile step, use `cargo-zigbuild` or `cross` in CI to produce all six target binaries, then hand them to GoReleaser/nfpm as prebuilt artifacts. GoReleaser can invoke cargo directly, but pre-building with zig/cross is the most reliable path for musl + aarch64.

### 10. Recommended end-to-end architecture (opinionated)
**Repo layout: per-tool repos, not a monorepo.** Each tool gets independent versioning, tags, changelog, and release cadence — which maps cleanly onto per-tool packages and one shared tap. A monorepo forces shared version tags or tag-prefix gymnastics and complicates GoReleaser/nfpm config; only use one if the tools genuinely release in lockstep. Create **one** `homebrew-<yourname>` tap repo shared by all tools.

**Stack:** per-tool repo → GoReleaser on tag → (cargo-zigbuild for Rust / passthrough for shell) → nfpm builds deb+rpm → signed GitHub Release → push deb/rpm into a self-hosted static apt/rpm repo (aptly + createrepo_c on object storage/GitHub Pages), **or** Cloudsmith's free OSS tier → GoReleaser commits the formula to your tap.

**Example `nfpm.yaml`:**
```yaml
name: "tool"
arch: "${ARCH}"          # amd64 / arm64; nfpm maps to x86_64 etc. for rpm
platform: "linux"
version: "${VERSION}"    # deb requires a leading digit; strip the v prefix
section: "utils"
priority: "optional"
maintainer: "You <you@example.com>"
description: "One-line description of tool."
vendor: "You"
homepage: "https://github.com/you/tool"
license: "MIT"
contents:
  - src: ./target/release/tool
    dst: /usr/bin/tool
    file_info: { mode: 0755 }
  - src: ./completions/tool.bash
    dst: /usr/share/bash-completion/completions/tool
    file_info: { mode: 0644 }
  - src: ./completions/_tool
    dst: /usr/share/zsh/vendor-completions/_tool
    file_info: { mode: 0644 }
  - src: ./completions/tool.fish
    dst: /usr/share/fish/vendor_completions.d/tool.fish
    file_info: { mode: 0644 }
  - src: ./man/tool.1
    dst: /usr/share/man/man1/tool.1
    file_info: { mode: 0644 }
  - src: ./config/tool.toml
    dst: /etc/tool/tool.toml
    type: config|noreplace
deb:
  signature: { key_file: "${GPG_KEY_FILE}" }
rpm:
  signature: { key_file: "${GPG_KEY_FILE}" }
```
Build locally: `nfpm pkg --packager deb --target . && nfpm pkg --packager rpm --target .`

**Install commands your users run:**
```bash
# Debian/Ubuntu
curl -fsSL https://repo.example.com/gpg.key | sudo gpg --dearmor -o /usr/share/keyrings/example-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/example-archive-keyring.gpg] https://repo.example.com/apt stable main" | sudo tee /etc/apt/sources.list.d/example.list
sudo apt update && sudo apt install tool

# Fedora/RHEL
sudo tee /etc/yum.repos.d/example.repo <<'EOF'
[example]
name=Example
baseurl=https://repo.example.com/rpm/
enabled=1
gpgcheck=1
gpgkey=https://repo.example.com/gpg.key
EOF
sudo dnf install tool

# macOS / Linux (Homebrew)
brew tap you/yourname
brew install tool
```

## Recommendations
1. **Now (week 1):** Standardize repo hygiene across tools (README, `MIT OR Apache-2.0`, semver tags, git-cliff changelog, ship man pages + completions). Stop new git-subtree vendoring; leave existing subtrees in place until packages exist, then migrate consumers to package installs.
2. **Week 2 — pick the pipeline:** Adopt **GoReleaser + nfpm** per tool with a tag-triggered GitHub Actions release. For Rust, add `cargo-zigbuild`/`cross` for the six-target matrix; publish to crates.io too.
3. **Week 3 — distribution:** Create one `homebrew-<name>` tap and let GoReleaser auto-update it. Stand up a **static apt+rpm repo** (aptly + createrepo_c on object storage/GitHub Pages) with a dedicated GPG signing key in CI secrets — **or** skip hosting entirely with **Cloudsmith's free OSS tier** if you'd rather not own metadata/keys.
4. **Week 4 — reach (optional):** Add **Fedora COPR** and **OpenSUSE Build Service** to widen distro coverage with minimal extra work (OBS builds both deb and rpm across distros from one source).
5. **Only if a tool gets real traction:** pursue homebrew-core, Debian ITP+sponsorship, or Fedora package review. **Thresholds that change the recommendation:** ≥75 stars *and an external submitter* → homebrew-core viable (≥225 stars if you self-submit); a distro user files/requests packaging → Debian ITP worth it; sustained >tens-of-GB/month download traffic → move off free hosted tiers to self-hosted static + CDN.

## Caveats
- **Official-registry acceptance for small personal tools is unlikely and slow.** homebrew-core, Debian, and Fedora all deliberately gate on notability/maintenance burden, not code quality. Invest your effort in self-hosted + tap + COPR/OBS, which have no such gate.
- **cargo-dist's future is uncertain** (vendor axo.dev wound down; single-maintainer + unofficial Astral fork; issue creation restricted). Using GoReleaser+nfpm avoids that risk and also covers your shell tools, which cargo-dist does not. No formal shutdown/handover notice from axo.dev was located — the wind-down is inferred from the parked commercial site, the removal of Axo Releases in v0.29.0 (2025-07-31), and the author's move to Astral.
- **Self-hosting shifts ongoing burden to you:** GPG key rotation, repo metadata correctness, and uptime. A static repo on object storage minimizes but doesn't eliminate this. Hosted tiers trade that for pricing/lock-in risk.
- **musl static binaries** occasionally differ from glibc at runtime (DNS/NSS resolution, some crates that expect glibc); test the musl artifacts, don't assume parity. `cargo-zigbuild` with a pinned glibc target (e.g. `.2.17`) is an alternative if you want dynamic glibc binaries that run on old distros.
- **Pricing and free-tier limits for Cloudsmith/packagecloud/Gemfury change**; the $1.50/GB Pro overage and 50 GB OSS storage figures are current-2026 and should be re-verified before committing.
- **Homebrew notability numbers and the self-submission 3× multiplier are current policy but are periodically revised** — re-check `docs.brew.sh/Acceptable-Formulae` before submitting.
